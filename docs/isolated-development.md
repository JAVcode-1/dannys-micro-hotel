# Local development startup

## Local admin account

The owner's configured local username is admin. Use the password the owner configured; it is intentionally not repeated here. Its salted hash and individual identity live in ignored .quality/isolated-development/admin-account.json and survive full development restarts. Restart npm run dev after creating/changing this configuration. The sign-in page accepts usernames in isolated mode; the backend checks credentials and existing active-staff authorization. No Gmail/hosted Supabase account is implied. Local staff sessions require an issued token and may need a new sign-in after API restart. The older staff@example.test fixture remains available for synthetic compatibility.

Normal Express startup keeps booking/payment/operational mutations and optional modules closed. No environment flag opens production transactions. `createIsolatedApp` requires development/test mode and an explicitly configured loopback `staytrack_test` pool. Its readiness probe checks workflow tables and the physical-readiness function.

## Unified Online Booking local inspection

`npm run dev` is the default full-system startup. It applies all local migrations, including candidates 027/028, to its fresh disposable database. Open `/book` for rooms, Hall-only or mixed selections, or `/book?service=hall&setup=theater` and `/book?service=hall&setup=room` for preselected Hall setups. Each selection retains an independent schedule. The Hall uses existing configurable notice/hours/buffers; alternative setups reserve the same exclusive physical resource.

Configure a synthetic GCash QR and recipient in staff Settings. Create one common hold, submit one synthetic reference/screenshot for the full total, then verify the actual **synthetic** receiving record in staff Payments. A successful verification confirms all items and displays the same reservation in the staff dashboard and reservation details. Staff use the existing room assignment/check-in pages and Function Hall calendar separately. The private in-memory proof store and fixture mailbox never send data to real providers.

`node scripts/verify-unified-booking.mjs` runs only the critical unified transaction/financial regressions against a new disposable loopback PostgreSQL instance on port 55442. Compile shared/backend before running it. It applies all local migrations to that instance, seeds synthetic fixtures, runs the exported unified regression, generates `.quality/unified-booking/database.types.ts`, and shuts down. It never reads `.env`, invokes hosted Supabase, sends mail or processes a payment. The installed embedded PostgreSQL module is required; no automatic network installation or hosted fallback. This focused runner is separate from the formal production quality gate.

Run `npm run dev` from the repository root. The launcher does not read `backend/.env`; it clears hosted Supabase/database configuration for its child processes, creates a fresh disposable loopback PostgreSQL database, applies local migrations there, and starts the fixture API on 127.0.0.1:3001 and frontend on 127.0.0.1:5173. All rooms are labelled SYNTHETIC and require a current staff inspection before Ready. The synthetic15-minute buffer is fixture configuration, not owner approval.

The launcher installs missing workspace dependencies automatically using the existing npm lockfile. It reuses cached embedded PostgreSQL tooling or installs pinned embedded-postgres 17.11.0-beta.19 into ignored .quality/postgres-tools/ on first startup. That first setup needs registry access if dependencies are not cached; later starts reuse them. An existing local module may optionally be selected with EMBEDDED_POSTGRES_MODULE, but no environment setting or extra command is required for ordinary startup. Setup failures stop startup rather than using a hosted database.

The API runs directly from backend/src/isolated-server.ts using the installed tsx loader and Node watch mode; Vite handles frontend changes. No build is part of development startup. The frontend starts after the API advertises isolated mode and passes its local readiness endpoint, and its proxy targets the same explicit 127.0.0.1:3001 address. This avoids stale backend/dist code and frontend/backend capability mismatches. Ctrl+C stops the local composition. A new disposable database is created on each full restart; the fake private image store and mailbox are also temporary.

The root dev:isolated script is only a compatibility alias for npm run dev. Production server scripts/configuration are unchanged; neither development entry point accepts NODE_ENV=production. Room readiness, staff verification of synthetic payments and all guest/staff authorization checks remain required.

Fixture credentials: guest@example.test uses OTP123456; staff@example.test uses password `development-only`. These are exclusively local fixture identities. Tokens are randomly generated per startup and accepted by exact match; JWT-shaped subjects only support subject-scoped UI retries. The frontend waits for /guest/booking-status before rendering. It selects fixture Auth and Hall/booking capabilities only under Vite development mode and a loopback browser hostname when the API explicitly reports isolatedDevelopment, bookingEnabled, hallEnabled, unifiedEnabled and paymentsEnabled. The frontend environment flag alone does not enable workflows. An unavailable API leaves capabilities closed; reload after the isolated API is ready. The API watches source changes; after a full restart use the same npm run dev command and reload the browser to refresh local fixture sessions. Real provider integrations remain closed.

Configure/upload a synthetic GCash QR through staff Settings before exercising guest payment. Browser flow: rooms → booking selections → email verification → server quote and policy/contact review → atomic hold → owned payment/proof → staff actual-ledger checks using synthetic evidence → confirmed item. The API integration regression exercises this flow and rejects foreign ownership. Uploading a screenshot alone never confirms anything.

`/development/mailbox` exposes only this disposable fixture mailbox; no real email is sent. The local scheduler runs every30seconds. `/development/jobs` also runs a bounded job batch. Review delivery is queued atomically with credentials and scoped consent; stale/revoked credential messages are cancelled. Private payment images use the fixture in-memory store and disappear on restart. This is not production Storage acceptance.

For multi-instance deployment, apply/review candidate025 separately and configure `RATE_LIMIT_MODE=postgres`; the default memory limiter is for single-process operation. Configure `TRUSTED_PROXY_CIDRS` with exact proxy addresses/CIDRs, never arbitrary forwarding trust. Shared counters store address digests and expire through jobs. The real email adapter must honor the message ID as a durable provider idempotency key before activation.

Database verification uses the existing disposable runner `.quality/h01/run-db.mjs` and `TEST_DATABASE_URL` restricted by tests to loopback/staytrack_test. The suite generates `.quality/database.types.sprint.ts` from the actual catalog through `scripts/generate-isolated-types.mjs`; copy/review that artifact into shared types only after the full migration suite passes. No hosted type-generation command is required or authorized by this sprint.

Production blockers remain: real inventory identifiers/readiness reconciliation, hotel QR/payee verification, official email/provider setup, owner/legal/privacy policy acceptance, real staff/device checks, hosted migrations and formal production quality gate. No automated refunds, fiscal receipt claim, ID photographs or new permission tiers are introduced. Unified guest Hall booking is available only inside this explicit isolated composition; normal production mutations remain closed. See [implementation evidence](unified-online-booking-requirements-sync.md).

## Normal startup supersedes the fixture default � 2026-11-22

The earlier statements that npm run dev starts this harness are superseded. Normal startup now runs backend/src/server.ts with backend/.env and passes matching public Auth configuration to Vite. It does not create databases, apply migrations, seed records or use fixture staff authentication. npm run dev:isolated is the explicit harness command. Its fixture operations remain separate from hosted acceptance. Hosted mutations are still gated in normal Express; changing startup does not activate them.
