## Shared expiry and proof protection

`createGuestHold` creates room claims and any online Hall item inside the same `claimTransaction`. Room claim insertion and `insertOnlineHall` both use PostgreSQL transaction-stable `now() + interval '30 minutes'`, so a mixed reservation gets the same deadline. Hall-only reservations receive that deadline too. Both channels schedule the existing 15- and 25-minute email reminder records without duplicating them.

`submitPaymentProof` locks the reservation and the room/Hall items, rejects a deadline already reached, and changes **all** selected items to `proof_pending_review` in one transaction. It cancels scheduled payment reminders. A successful upload/receipt is still pending review, never confirmation. Staff delay cannot release these protected items.

Migration 027's `expire_online_holds` locks the Hall resource and reservation/items, and releases the Hall and sibling room holds together only for expired, still-held reservations without a payment submission. `expireClaims` then handles remaining room-only held claims; neither path expires `proof_pending_review`. The hosted development timer calls this every 30 seconds, so cleanup may occur on the next tick after the deadline. Proof acceptance checks database time directly and does not gain extra time from scheduler lag. Previously paid-late cases require staff reconciliation and guest consent/manual refund handling. Verify races and Hall-only/mixed cases during acceptance; this review does not establish that those checks passed.
